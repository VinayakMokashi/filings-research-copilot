Item 1 · Business

What it does

The target design, built across Phases 2 to 7.

Text

Reads the filings

Works out which filings a question is about, rewrites it three ways and searches page-sized chunks of those filings. Every sentence in the answer cites a page, a calculator does the arithmetic, and it says so when the pages don't hold the answer.

Numbers

Runs the numbers

Turns questions about reported figures into read-only SQL over XBRL facts, with hints that link the question's companies and metrics to the database. The database does the arithmetic, and on FinanceBench's dev figure questions it is right 32 times in 33.

Briefs

Writes the brief

For longer requests, a planner outlines the brief, writers draft sections in parallel, and an editor and a critic check each claim before it reaches you.

One question, end to end

“How did 3M's capital expenditure change from FY2018 to FY2022, and what did management say drove it?”

  1. 1Understand

    Company 3M (CIK 0000066740), fiscal years 2018 to 2022, annual reports (10-K).

  2. 2Route

    The question needs numbers and narrative, so it goes to both the data agent and the doc agent.

  3. 3Data agent

    Read-only SQL over XBRL facts tagged us-gaap:PaymentsToAcquirePropertyPlantAndEquipment, one value per fiscal year.

  4. 4Doc agent

    Dense search over page-sized chunks of 3M's 10-Ks for passages about capital spending, with the question and three rewrites of it; the best chunks become numbered sources.

  5. 5Validate

    Each sentence is checked against its cited page or query result. Unsupported claims trigger a retry or are dropped.

  6. 6Respond

    An answer with numbered citations, a five-year chart, and the SQL one click away.

Every step works today: a LangGraph graph routes the question, both agents answer, the validator checks each cited sentence, and the answer streams to the web UI with its chart and SQL (Phases 2 to 6).

Design note

Numbers and narrative come from different systems on purpose. XBRL facts are exact; filing text explains them.

The validator makes the two agree before anything is shown.

Resolves the filings a question names, rewrites it three ways, searches page-sized chunks with dense vectors and answers from numbered sources in one call, citing every sentence and leaving arithmetic to a calculator. Every result is reported with a 95% bootstrap confidence interval. A change ships only when its paired improvement on the dev set is significant. The held-out test set is opened only at milestones. On dev, the Phase 2 baseline (dense search over page chunks) puts an evidence page in its top 20 for 77% of questions when it searches the right filing, against 29% for that filing's first 20 pages, and for 52% when it searches all 84 filings. Keyword routing is right 62% of the time, and the XBRL facts database reproduces all 33 FinanceBench metrics answers. In Phase 3 the doc agent answers 65% of dev questions correctly (0.56 to 0.74), and 88% of those that ask for a figure, by an LLM judge that agreed with all 41 reference labels from a stronger model, not a person; 63% of its answers are supported sentence by sentence by their citations, at about a tenth of a cent per question. In Phase 4 the data agent's SQL is right on all 14 questions of the held-out SQL test split (exact 95% interval 0.77 to 1.00), and on FinanceBench's 33 dev figure questions it answers 32 correctly by the same judge, against the doc agent's 29. In Phase 5 an LLM router on gpt-oss-120b sends all 138 dev questions and all 60 held-out test questions to the right specialist (exact 95% interval on test 0.94 to 1.00), with a semantic router (0.74 on dev) as its fallback. The validator raises the share of answers supported sentence by sentence from 0.63 to 0.85, at a cost: correctness falls from 0.65 to 0.61, because judgement questions lose the sentences it can't verify. The rebuilt hybrid agent states every expected figure on all 13 of its questions, against 10 for the doc agent alone. End to end, the copilot answers 49% of the dev questions correctly, against 65% for the doc agent alone on the same provider and judges (p = 0.0003): its data agent answers 31 of the 33 figure questions and its text answers are more often fully supported (0.76 against 0.43), but analyst questions sent to the data agent and the validator's trimming cost more than that gains. A version 2 that hands such questions on is Phase 7's first experiment.

Lesson carried over

In text2sql-analyst, an earlier project, the same code scored 100% and then 95% on a re-run. Small eval sets need confidence intervals.

Item 9A · Controls and procedures

Guardrails

Controls built across Phases 3 to 8. The secret scan in CI runs. Since Phase 3 answers cite their pages, refuse when the evidence is missing, and leave arithmetic to a sandboxed calculator; since Phase 4 the data agent runs only single read-only queries; since Phase 6 the API enforces daily quotas, quotes instruction-like text out of retrieved pages, and serves repeated questions from a cache.

SQL

One read-only SELECT, checked by sqlglot and run on a read-only connection, under an authorizer that refuses anything but reads, with a 10-second timeout, a 200-row cap and a 1 MB cap per value. In production, a read-only database role too.

Evidence

Every claim cites a page or a query. Unsupported claims are dropped, and with no evidence the copilot says so.

Retrieved text

Filing text reaches the model as quoted data: sentences that read as instructions to an assistant are replaced before any prompt, and a scan of all 53,901 parsed pages found none. Every tool is read-only.

Arithmetic

The model writes the expression and a sandboxed calculator computes it.

Cost and abuse

Daily quotas per visitor and in total, input limits, a cache for questions asked word for word before, and a Cloud Billing budget alert. A semantic cache was measured and rejected: questions with their measure swapped looked more alike than true paraphrases.

Keys

Locally, keys sit in a git-ignored .env, and CI scans the full git history for secrets on every push and pull request. On Google Cloud, GitHub will deploy through Workload Identity Federation, so no service-account keys are stored, and third-party API keys will be loaded from Secret Manager.

Design note

There will be no long-lived cloud credentials: each service runs as its own service account, and GitHub deploys through Workload Identity Federation. Third-party API keys are long-lived, so they stay out of code and images and are loaded from Secret Manager.

Item 2 · Properties

Where it runs

Planned for Phase 8. Today the project runs locally with Docker Compose.

Demo windows

Cloud Run scales the services to zero, so they stay deployed and cost nothing while idle. The database, the one part that costs money idle, runs only in demo windows: one command starts it and another stops it, with costs measured in Phase 8.

Its storage stays between demos, with backups in Cloud Storage. Day to day, the project runs locally with Docker Compose.

Item 1A · Risk factors

Risks, and how they're handled

RiskHow it's handled
Free-tier rate limits on GroqLiteLLM falls back to other providers, and Cerebras serves the same open models; an answer cache and daily quotas cut repeat calls.
Answers vary between runsRepeated eval runs, and confidence intervals on every metric.
Models may have seen FinanceBench or well-known filingsA held-out split and synthetic questions on recent filings; memorisation is noted next to results.
XBRL tags differ between companiesA tested mapping from each company's tags to canonical metrics.
PDF tables flatten badlyNumbers come from XBRL. Page-sized chunks keep each financial statement whole, which ranked statement evidence first far more often (MRR 0.60 against 0.42 with 480-token chunks).
No CUDA GPU on the development machineFine-tuning runs on free Kaggle or Colab GPUs; small models are served on CPU with ONNX.
Cloud costsA budget alert comes first, Cloud Run scales to zero, the database runs only in demo windows, and a scheduled job stops it if it is left running.
